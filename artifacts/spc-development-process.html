Development Operating System

Use structure for control, not bureaucracy.

The app is improving, but the process needs visible checkpoints so you feel in control. The goal is not to become a software engineer overnight. The goal is to run a clear product-quality loop with me doing the implementation work.

Your roleProduct owner + quality engineer
Agent rolePlan, code, test, explain
Unit of workOne work card
Safety ruleCode -> test -> commit

Role Split

You own product truth
  • Real usage problems
  • Screenshots and files
  • What feels wrong
  • What good should look like
  • Final visual judgment
I own engineering execution
  • Work cards
  • Priority and scope
  • Implementation plan
  • Code changes and tests
  • Commit checkpoints
You do not need to become the coder. You need to become a clear product owner and quality judge.

Core Loop

1Observe
Use the app normally and send rough issues.
2Capture
I turn each issue into a work card.
3Select
We pick one P1/P2 card to fix.
4Build
I implement, test, and commit.
5Review
You check the app visually.

Rules

Rule Why
One meaningful change needs one work card. Prevents random edits and keeps intent visible.
Do not fix ten things together. Large mixed changes are hard to test and hard to undo.
Commit after a coherent batch. Creates a recoverable checkpoint.
Chart changes require visual evidence. Unit tests can pass while the chart still looks wrong.
Planning should be short unless risk is high. Enough structure to stay safe, not enough to slow the work.
The failure mode to avoid: chat becomes the product spec, issue tracker, test log, and release checklist all at once.
