AI Output Standard

Use HTML when the report is too dense for Markdown.

Based on the Karpathy note in the vault: durable knowledge stays in Markdown, but complex explanations, plans, reviews, and visual evidence should be delivered as local HTML artifacts.

ScopeLong reports, reviews, plans, tests
DefaultMarkdown for short, HTML for dense
MemoryMarkdown companion file
OutputLocal browser-readable artifact

Core Decision

Rule: HTML is the presentation layer. Markdown is the memory layer.

For simple answers, chat Markdown is enough. For complicated reports, HTML gives better scanning, layout, tables, diagrams, color-coded evidence, and navigation. The point is not decoration. The point is lowering review effort.

Keep in Markdown
  • Permanent vault notes
  • Short answers
  • Small decisions
  • Diff-sensitive project docs
Render as HTML
  • Long codebase reports
  • Agent-team summaries
  • Visual QA reports
  • Feature planning dashboards

When to Use HTML

Use HTML when two or more of these are true:

Trigger Why HTML Helps
More than 6 sectionsNavigation and visual hierarchy prevent scrolling fatigue.
3+ options comparedTables and cards make tradeoffs visible.
5+ files referencedFile maps and grouped evidence reduce confusion.
Screenshots or charts includedHTML can place visual evidence next to interpretation.
User must approve a decisionDecision blocks make the required action explicit.
Report will be reusedA local artifact is easier to reopen than a long chat answer.

Required Structure

1Summary
5-8 bullets on what matters.
2Status
Scope, confidence, date, decision needed.
3Evidence
Files, screenshots, tests, observations.
4Decision
What the user needs to approve.
5Action
Prioritized next steps.
First screen test: within 30 seconds, the user should know what changed, why it matters, what to review, and what action is next.

Report Types

Architecture Report Module map, data flow, deepening opportunities, testability impact, risks.
Bug Report Reproduction, expected vs actual, evidence, root cause, fix plan, regression tests.
Visual QA Report Test status, screenshot paths, chart checks, pass/fail conclusion.
Feature Plan User problem, proposed workflow, scope, slices, open decisions.
Agent-Team Report Agent roster, assignments, outputs, conflicts, lead-agent review.
Decision Report Options, tradeoffs, recommended choice, consequences, rollback path.

Design Rules

Rule Standard
Lead with findingsDo not make the user read the process before the conclusion.
Color has meaningBlockerRiskVerifiedInfo
Tables for comparisonUse tables for options, priorities, files, and pass/fail matrices.
Cards for repeated itemsUse cards for repeated report objects, not as generic decoration.
Evidence close to claimsPut screenshots, file paths, or tests near the statement they support.
Copy/export blockFor reusable decisions, include copyable Markdown or JSON.

Workflow

  1. Decide whether the output is short Markdown or complex HTML.
  2. If complex, create a Markdown companion file for durable decisions.
  3. Create the HTML artifact under artifacts/.
  4. Keep the first screen focused on summary, status, and review action.
  5. Use evidence sections for files, screenshots, tests, and observations.
  6. End with a short action plan.
Recommended pairing: docs/communication/<topic>.md for durable rules and artifacts/<topic>.html for visual review.

Reusable Prompt

Use this when you want future agents to produce this kind of output.

Create an HTML artifact for this report because the output is complex. Use: - executive summary at the top - sticky navigation - visual hierarchy with cards, tables, callouts, and diagrams - evidence section with file paths, screenshots, or test results - decision section showing what I need to review - action plan sorted by priority Also create or update a Markdown companion file if the result should become durable project knowledge. Keep Markdown as memory and HTML as the reading layer.
